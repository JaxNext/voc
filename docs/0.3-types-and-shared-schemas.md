# Step 0.3: Types & Shared Schemas Implementation Record

This document records the implementation process and verification results for **Task 0.3 (Types & Shared Schemas)** as defined in [development-plan.md](./development-plan.md) and [tech-design.md](./tech-design.md).

## 1. Overview & Objectives

Task 0.3 closes the gap between the database layer (0.2) and the application code that will consume it (Phase 1+):

- Declare a TypeScript `Database` type matching the SQL migration so `@nuxtjs/supabase`'s `useSupabaseClient<Database>()` / `serverSupabaseClient<Database>()` helpers are fully typed.
- Define a single source of truth for **input validation** (Zod schemas) at the API boundary, covering records, tags, and review grades.

Both files live under `app/types/`, which maps to `~` and `@` in Nuxt 4 and to `~` in the Vitest alias config.

## 3. Design Decisions

### 3.1 `Database` type — hand-written, Supabase-compatible

`app/types/database.ts` exports the standard Supabase `Database` shape:

```ts
type Database = {
  public: {
    Tables: { records: { Row; Insert; Update; Relationships } /* … */ }
    Views: { [_ in never]: never }
    Functions: { [_ in never]: never }
    Enums: { record_type; learning_status; grade }
    CompositeTypes: { [_ in never]: never }
  }
}
```

- Each table exposes `Row` (read shape), `Insert` (write shape), and `Update` (partial-write shape), exactly matching the format produced by `supabase gen types typescript`. `Insert` / `Update` mark the database-side defaults (`id`, `user_id` from auth, `created_at`, `updated_at`) as optional.
- Three enum string unions (`RecordType`, `LearningStatus`, `Grade`) are exported both as TS types and as Supabase `Enums` entries, so PostgREST `enum`-typed columns come back strongly typed.
- The file is **hand-written** today because no live Supabase project exists yet. When one is connected, the same file can be overwritten with `supabase gen types typescript --project-id <id>` — the shape is a drop-in replacement.
- Wired in `nuxt.config.ts` via `supabase: { types: '~/types/database' }`. After `nuxt prepare`, the module writes a re-export shim at `.nuxt/types/supabase-database.d.ts`:

  ```ts
  export * from '../../app/types/database.ts'
  ```

  …so `useSupabaseClient<Database>()` resolves correctly throughout the app.

### 3.2 Zod schemas — single source of truth at the boundary

`app/types/records.ts` exports schemas (with inferred TS types and runtime enum constants) covering every input the API or form layer needs to validate:

| Schema                 | Used by                                         | Notes                                                                                                                  |
| ---------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `RecordTypeSchema`     | `RecordInputSchema.type`                        | Matches the `record_type` enum (`word                                                                                  | phrase   | sentence`). |
| `LearningStatusSchema` | future use (read state, filters)                | Matches the `learning_status` enum (`new                                                                               | learning | mastered`). |
| `GradeSchema`          | `ReviewGradeSchema.grade`                       | Matches the `grade` enum (`forgot                                                                                      | hazy     | know        | easy`). |
| `TagInputSchema`       | `POST` tag create flow                          | `name` is trimmed, length-bounded (1–50). `is_predefined` is not accepted — only the seed sets it.                     |
| `RecordInputSchema`    | `RecordForm` (create + edit) and any future API | `type`, `content`, `meaning` required; `source`, `notes` optional; `tagIds` defaults to `[]` and is an array of UUIDs. |
| `ReviewGradeSchema`    | `POST /api/review/grade` body                   | `{ record_id: uuid, grade: enum }`.                                                                                    |

#### Length limits

Realistic but generous:

- `content` ≤ 500
- `meaning` ≤ 2000
- `source` ≤ 500
- `notes` ≤ 4000
- `tag name` ≤ 50

These are client-side guard rails — Postgres `text` columns are unbounded. They prevent obviously-broken payloads while leaving headroom for long sentences and detailed notes.

#### Trimming

`content`, `meaning`, `source`, `notes`, and tag `name` are all `.trim()`-ed before length checks, so a payload of `"   "` is rejected the same as `""` and never stored as a row of whitespace.

#### UUIDs

Use Zod v4's standalone `z.uuid()` (the `z.string().uuid()` form is deprecated in v4).

### 3.3 Inferred TypeScript types

Every schema also re-exports a TS type via `z.infer<...>`, so consumer code never duplicates the shape:

```ts
export type RecordInput = z.infer<typeof RecordInputSchema>
export type TagInput = z.infer<typeof TagInputSchema>
export type ReviewGrade = z.infer<typeof ReviewGradeSchema>
```

The enum-typed constants (`RECORD_TYPES`, `REVIEW_GRADES`) are also exported, so UI components (e.g., `RecordForm.vue`'s type chips) can iterate over the same set the validator enforces.

All four local checks were run after the changes:

| Command             | Result                                                               |
| ------------------- | -------------------------------------------------------------------- |
| `pnpm lint`         | `0 warnings and 0 errors` (7 files, 117 rules).                      |

The new test file `tests/unit/schemas.test.ts` contributes 24 of those 25 tests (the original sanity test is still in `example.test.ts`). Coverage per schema:

- `RecordTypeSchema`, `LearningStatusSchema`, `GradeSchema` — accept every valid value, reject unknown values.
- `TagInputSchema` — accepts valid names, trims whitespace, rejects empty/whitespace/oversize/missing.
- `RecordInputSchema` — accepts a minimal record (with default `tagIds: []`), trims content & meaning, accepts optional `source` / `notes` / `tagIds`, rejects invalid type, empty/oversize fields, and non-UUID tag ids.
- `ReviewGradeSchema` — accepts a `{ record_id, grade }` payload, rejects non-UUID `record_id`, invalid grade, and missing fields.

The Supabase type re-export shim at `.nuxt/types/supabase-database.d.ts` confirms the `nuxt.config.ts` wiring:

```ts
export * from '../../app/types/database.ts'
```

## 5. Deviations from the plan

- **No `database.ts` is generated**, because no live Supabase project is available yet. The plan allowed both options ("generate or declare"). The hand-written file is byte-compatible with `supabase gen types typescript` output, so a future regeneration is a one-line replacement.
- **One additional schema** (`LearningStatusSchema`) and the two enum constants (`RECORD_TYPES`, `REVIEW_GRADES`) were added beyond the three required (`RecordInputSchema`, `TagInputSchema`, `ReviewGradeSchema`). They are zero-cost and are reused in tests and in the inferred types — no new types or files were created to support them.
