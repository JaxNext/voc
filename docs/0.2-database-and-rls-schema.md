## 3. Schema Design & Decisions

### 3.1 Enums

- `record_type`: `word | phrase | sentence` — one row per captured item.
- `learning_status`: `new | learning | mastered` — drives the due-query filter (`status <> 'mastered'`).
- `grade`: `forgot | hazy | know | easy` — self-grading options stored in `review_events`.

### 3.2 Tables

Followed [tech-design.md §5](../docs/tech-design.md) 1:1:

| Table           | Key points                                                                                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `records`       | `user_id → auth.users` (cascade delete); `content`/`meaning` required; `source`/`notes` optional.                                                                                                                                   |
| `tags`          | `user_id` **null** = predefined (shared); non-null = user-owned. `is_predefined` boolean flag.                                                                                                                                      |
| `record_tags`   | Composite PK `(record_id, tag_id)`, both FKs cascade.                                                                                                                                                                               |
| `review_states` | One row per record (`record_id` PK → `records`); SRS fields `status`, `interval_days`, `consecutive_pass`, `last_reviewed_at`, `next_review_at`. `next_review_at` defaults to `now()` so a newly created record is immediately due. |
| `review_events` | Append-only log; `user_id` denormalized onto the event so stats/streak queries do not need a join.                                                                                                                                  |

### 3.3 Deviations / refinements vs. the raw tech-design sketch

These are deliberate improvements documented here:

1. **Tag-name uniqueness via partial indexes.** A plain `unique (user_id, name)` does not protect predefined tags, because in Postgres NULL values never collide — so two rows `(NULL, 'work')` would both pass. Replaced with two partial unique indexes:
   - `tags_custom_name_unique` on `(user_id, name)` where `user_id is not null`.
   - `tags_predefined_name_unique` on `(name)` where `is_predefined`.
2. **`updated_at` trigger.** Added `set_updated_at()` function + `records_set_updated_at` trigger so `records.updated_at` stays correct on every `UPDATE` without each write path having to remember it.
3. **Explicit `GRANT`s.** RLS policies are inert without table privileges, so `authenticated` receives `select/insert/update/delete` on all five tables and `anon` receives `select` on `tags` (predefined tags are public by design). The Nitro server keeps using `service_role`, which bypasses RLS.
4. **Schema-qualified identifiers** (`public.*`, `auth.users`) so the migration does not depend on `search_path`.

### 3.4 Indexes

Exactly the three hot-query indexes from the design:

- `idx_records_user_created` → `records (user_id, created_at desc)` — newest-first list per user.
- `idx_review_due` → `review_states (next_review_at)` **partial**, `where status <> 'mastered'` — due-session query.
- `idx_events_user_date` → `review_events (user_id, reviewed_at)` — per-day stats/streak.

### 3.5 RLS policy matrix

Policies are owner-scoped; identity always comes from `auth.uid()`, never from a client-supplied `user_id`.

| Table           | Policy                     | Rule                                                               |
| --------------- | -------------------------- | ------------------------------------------------------------------ |
| `records`       | `records owner all`        | `auth.uid() = user_id` (USING + WITH CHECK)                        |
| `tags`          | `tags predefined readable` | `SELECT` where `is_predefined` (everyone)                          |
| `tags`          | `tags owner all`           | `auth.uid() = user_id` for custom tags                             |
| `record_tags`   | `record_tags owner all`    | row must reference a record where `records.user_id = auth.uid()`   |
| `review_states` | `review_states owner all`  | same "through parent record" ownership check (no `user_id` column) |
| `review_events` | `review_events owner all`  | `auth.uid() = user_id`                                             |

Note: `review_states`/`review_events` insert/update flows are executed server-side with `service_role`, but SELECT-level policies still keep any direct client access safe, and the WITH CHECK clauses close the loop for completeness.

### 3.6 Seed: predefined tags

```sql
insert into public.tags (name, is_predefined)
values ('work', true), ('daily', true), ('idiom', true), ('travel', true)
on conflict (name) where is_predefined do nothing;
```

`ON CONFLICT` targets the partial unique index, so re-running the migration (or re-applying on a database that already has some tags) cannot duplicate entries.

## 4. Verification Status

- **Static review**: SQL hand-reviewed against the data model in [tech-design.md §5](../docs/tech-design.md) and the AGENTS.md data-model conventions — enum values, FK/cascade relationships, index expressions, and policy predicates all match.

  2. Verify User A cannot read/write User B's records or custom tags (the acceptance test from development-plan.md §4).
  3. Verify predefined tags are visible to any role and custom tags only to their owner.
