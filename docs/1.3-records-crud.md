## 1. Overview & Objectives

The composable is the data layer for all record operations:

- **Fetch records** — paginated, sorted, filtered by type & tags, with case-insensitive text search across `content` and `meaning`.
- **Create a record** — inserts into `records`, tags into `record_tags`, and initializes `review_states`.
- **Update a record** & sync its tag associations.
- **Delete a record** (FK cascades remove `record_tags` / `review_states` / `review_events`).

Architecture per [AGENTS.md](../AGENTS.md) rule 1: records are plain CRUD, so the composable talks to **PostgREST directly** through `useSupabaseClient()` with the user's session token — **no Nitro route**. [RLS](../supabase/migrations/001_initial_schema.sql) scopes every row to its owner.

## 3. Design Decisions

### 3.1 Query-only composable (no shared `useState`)

Unlike tags (one small list legitimately shared app-wide, [1.2 doc §3.1](./1.2-tag-management.md)), records are paginated and filtered per view. List state (current page, filters, accumulated results for infinite scroll) belongs to the consumer (1.4 index page), and detail state to the detail page. The composable therefore exposes stateless query/action functions — simpler to reason about, no cross-view cache invalidation problems.

### 3.2 List query: one round trip, exact count, embedded tags

`fetchRecords` issues a single query: `select('*, record_tags(tags(*))', { count: 'exact' })` + `.range(from, to)`, returning `{ records, total, hasMore }` — `hasMore` drives 1.4's infinite-scroll indicator without an extra count round trip. Default `pageSize` is 20. Rows are mapped to `RecordWithTags` (`tags: Tag[]` flattened from the embed; null embeds are skipped). Sort orders append `.order('id')` as a tiebreak so equal `created_at`/`content` values paginate stably.

### 3.3 Tag filter: union semantics via two-step query

Multiple active tags mean "records carrying **any** of them" (tapping filter chips widens the net, per product-design §6.2). Implemented as two queries: collect matching `record_id`s from `record_tags` (deduped via `Set`), then `.in('id', ids)` on the list query. Rationale: a single `record_tags!inner` join would duplicate records carrying several matching tags, corrupting both the page contents and the exact count. Empty match set short-circuits to `{ total: 0 }` with no second query. Scale note: very large id sets grow the URL — fine at MVP scale, revisit with an RPC if ever needed.

### 3.4 Search: `ilike` across content OR meaning

The search term is matched case-insensitively against `content` **or** `meaning` via PostgREST's `or=` filter. The `or=` parameter syntax reserves commas/parens, so user input has `,()` stripped before interpolation — it cannot inject additional filter branches. `%` and `_` still act as SQL wildcards (an accepted MVP nuance; no tsvector column exists in the schema).

### 3.5 Create: sequential inserts + compensating cleanup

Three steps in order — record insert (`user_id` from the session, rule 4; RLS `with check` re-validates), `record_tags` rows (skipped when `tagIds` is empty), and a `review_states` row of just `{ record_id }` (DB defaults fill `status 'new'`, interval 0, `next_review_at = now()` → **due immediately**, matching the SRS intent). If any step after the record insert fails, the record is deleted again — the FK cascade cleans any partial tag/state rows — and the error propagates. The user never keeps a half-created record; trade-off (documented): the cleanup delete is itself best-effort.

### 3.6 Update: single-row update + diff-based tag sync

The row update uses `.select().single()` so a 0-row update (bad id or RLS-invisible) surfaces as an error, mapped via `PGRST116` → _"Record not found"_ — a plain `.update()` would silently "succeed" on 0 rows. Tag associations sync as a **diff** against the current rows (remove unselected, add newly selected): a failed tag write can never wipe existing associations, unlike a delete-all-then-reinsert approach. The returned row does not carry refreshed tags; the detail page refetches via `fetchRecord`.

### 3.7 Typed embeds required a `Relationships` fix

The hand-written [database.ts](../app/types/database.ts) had `Relationships: []`, so supabase-js's typegen format could not resolve the `record_tags(tags(*))` embed (`SelectQueryError: could not find the relation between records and record_tags`). Fixed by declaring the two FK relationships (`record_tags_record_id_fkey` → `records.id`, `record_tags_tag_id_fkey` → `tags.id`) using Postgres's auto-naming for inline `REFERENCES` — exactly the shape `supabase gen types` emits. This is a type-level-only change that also unblocks Phase 2's embeds (e.g. review states joined through records). `VocRecord` (not `Record`) avoids shadowing TypeScript's built-in utility type.

### 3.8 No unit test (yet)

Same rationale as the auth guard (1.1 §4) and `useTags` (1.2 §3.7): thin glue over Nuxt auto-imports + the Supabase client; the bare `vitest` config would test mocks. Coverage arrives with `tests/e2e/records.spec.ts` (create → list → filter → edit → delete).

## 7. RecordForm Implementation Record

### 7.1 Deliverable & contract

[RecordForm.vue](../app/components/RecordForm.vue) implements the mock in [product-design.md §6.3](./product-design.md): type chips (Word/Phrase/Sentence), Content\* / Meaning\*, Source / Notes (marked optional), Tags row, Save button. Edit mode is the same form pre-filled (mock: "Edit record").

- **Props/contract**: `record?: RecordWithTags` — absent → create mode, present → edit mode (prefills every field including `tagIds` from `record.tags`). **Pages must render the form only after data is loaded** (e.g. `v-if` on the fetched record) so prefill happens exactly once at setup.
- **Emits**: `success(record: VocRecord)` after a successful create/update — pages own navigation (new page → records home/detail, detail page → refetch); `cancel` from the edit-mode Cancel button.
- **Ownership**: the form calls `createRecord`/`updateRecord` from `useRecords` directly (same "component owns its data actions" pattern as `TagCreateInline`/`tags.vue`), and toasts success/failure itself for immediate feedback.

### 7.2 Design decisions

- **Zod is the single validation layer.** `UForm` receives `RecordInputSchema` — the exact schema `useRecords` enforces — so constraints live in one place; Nuxt UI renders per-field errors and (after a first submit attempt) validates eagerly. The composable's `parseInput` becomes a cheap double check, not duplicated logic. Client-only: DB/RLS remain the boundary of truth (architecture rule 4).
- **Empty optionals → `undefined`, not `''`.** The schema allows empty `source`/`notes`; before submission, empty strings are normalized to `undefined` so DB rows keep `null` semantics.
- **Type chips mirror the TagPicker chip styling** (rounded pills, `solid/primary` when active vs `soft/neutral`, `aria-pressed`) for a consistent chip language; `type="button"` prevents accidental form submits.
- **Save button lives at the bottom of the form** (block, full width) rather than the mock's top-right header slot: the page owns the header with back navigation, and a bottom button is the thumb-friendly spot on mobile (compact-control preference). Length constants (`MAX_CONTENT` etc.) are now exported from [records.ts](../app/types/records.ts) and bound as `maxlength` so inputs physically cannot exceed schema limits.
- **No dirty-check/draft persistence** at this stage — out of the plan's scope; the "Save as you go" loop is fast enough at MVP scale.

### 8.2 Design decisions

- **`new.vue` is a thin shell.** The form owns everything below the header; the page only routes the `success` event to `/records/${record.id}` so the user lands on what they just captured (confirming the create) instead of back to a list that doesn't exist yet (1.4).
- **Detail view states**: loading skeletons → `notFound` alert ("deleted, or belongs to another account" — `fetchRecord` returns `null` for both, §2) → edit mode (same `RecordForm`, `record` prop, per the §7.1 prefill contract) → read view.
- **Refetch after edit**: `updateRecord`'s return row carries no fresh tags (§3.6), so a successful edit closes the form and refetches via `fetchRecord`.
- **Delete asks for confirmation** (`UModal`, error-styled confirm) — asymmetric with tag deletion ([1.2 doc §7.2](./1.2-tag-management.md)): a record is the unit of the SRS loop and its `review_events` history is unrecoverable, so one tap must not destroy it. Non-uuid route params short-circuit to the not-found state via `z.uuid()` without hitting the API (avoids PostgREST's `22P02` uuid syntax error).
- **Edit in the header, Delete at the bottom** — matches the mock's prominent bottom "Delete record" while keeping Edit one thumb-reach from the content; the mock's `⋯` overflow menu is deferred (only two actions exist).
- `Added` uses `toLocaleDateString` (e.g. "Sep 12, 2026"); a shared relative-time helper arrives with `RecordCard` in 1.4, which also needs it.
