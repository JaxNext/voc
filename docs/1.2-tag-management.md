# Step 1.2: Tag Management — Implementation Record (Complete)

This document records the implementation process and verification results for **Task 1.2 (Tag Management)**, [development-plan.md](./development-plan.md) §1.2, as specified in [tech-design.md](./tech-design.md): the `useTags` composable (§1–§5), the `TagPicker.vue` component (§6), and the `app/pages/tags.vue` manager page (§7). **All 1.2 plan items are now checked off.**

## 1. Overview & Objectives

The composable is the data layer for everything tag-related:

- **Fetch** predefined tags (`is_predefined = true`, shared by all users) and the user's custom tags.
- **Create** a custom tag.
- **Delete** a custom tag.

Architecture per [AGENTS.md](../AGENTS.md) rule 1: tags are plain CRUD, so the composable talks to **PostgREST directly** through `useSupabaseClient()` with the user's session — **no Nitro route**. [RLS](../supabase/migrations/001_initial_schema.sql) is the defense: predefined rows are readable by everyone, custom rows only by their owner.

## 3. Design Decisions

### 3.1 One shared state, fetch-once semantics

Tag state lives in `useState('voc-tags')` rather than a per-instance `ref`, so `TagPicker` on every record form, the `/tags` page, and any future filter UI all render the **same list**, and `createTag`/`deleteTag` mutations propagate app-wide without manual refresh. Two mechanisms back `ensureLoaded()`: a per-request `useState('voc-tags-loaded')` flag skips work once data is loaded, and an **in-flight promise** (`__vocTagsLoad`, stored on `nuxtApp`) is shared by concurrent first-time callers — so two components mounting in the same tick trigger **one** Supabase request, not two. The promise deliberately lives on `nuxtApp` (per-request on the server, per-app on the client) instead of a module-level variable: a module-level promise would be shared across all server requests — the exact cross-request state-pollution trap this design avoids — and mirrors how Nuxt's own `useAsyncData` dedupes fetches (`nuxtApp._asyncDataPromises`). If the shared load fails, the flag stays false and the next caller retries with a fresh request. `load()` remains available for forced refreshes (e.g., after the tags page does an external mutation).

### 3.2 A single query covers both tag kinds

The `tags` RLS policies return exactly "all predefined rows + rows owned by the calling session" for any `select *`, so `load()` needs **no `user_id` filter** and no separate queries — one round trip, ordered predefined-first then by name. This keeps the client simple and lets the database remain the authority on visibility.

### 3.3 `createTag`: session-derived `user_id`, Zod boundary, friendly dup errors

- The `tags.user_id` column is nullable with **no default**, while the RLS `tags owner all` policy checks `auth.uid() = user_id` — so the insert payload must carry `user_id`. It is taken from `useSupabaseUser()` (the session), never from arbitrary caller input (AGENTS.md rule 4); RLS re-validates server-side regardless.
- Input is validated with the existing **`TagInputSchema`** (trim + 1–50 chars) — the single source of truth shared with `TagPicker`. Failures throw an `Error` carrying the first Zod message, so callers only ever catch plain `Error`s.
- The insert uses `.select().single()` to return the persisted row (with server-assigned `id`/`created_at`), which is appended to shared state.
- Postgres unique violation (`23505`, enforced by the partial unique index `tags_custom_name_unique`) is mapped to _"A tag with this name already exists"_ instead of a raw PostgREST message.

### 3.4 `deleteTag`: cascade semantics + double protection against deleting predefined tags

- `record_tags` rows referencing the tag disappear via the FK `on delete cascade` — deleting a tag silently un-tags records, which matches the schema's intent.
- Predefined tags are guarded twice: the composable throws up front if the id resolves to a predefined row, and RLS would reject the delete anyway (predefined rows have `user_id = null`, which never satisfies `auth.uid() = user_id`).
- Local state removes the row immediately after the delete succeeds.

### 3.5 Error normalization

All action methods throw plain `Error`s with user-presentable messages (via a small `describeError` helper): Zod issues → first message; `23505` → duplicate-name text; `PostgrestError` → its message; unknown → generic fallback. Callers (`TagPicker`, `/tags` page) can `try/catch` and feed `error.message` straight into a toast — UI concern stays in the component layer.

### 3.6 Sorting

Predefined tags sort by name (stable, seed order is meaningless); custom tags sort **newest-first** so a just-created tag is immediately visible (matches the "immediate feedback" UX preference).

### 3.7 No unit test (yet)

As with the auth guard (1.1 doc §4), the composable is thin glue over Nuxt auto-imports and the Supabase client; mocking `useState`/`useSupabaseClient` under the bare `vitest` config (no `@nuxt/test-utils`) would test the mocks, not the logic. Meaningful coverage arrives with the Playwright flows (`tests/e2e/records.spec.ts` covers tagging; an extension to `tests/e2e/auth.spec.ts`-style flows can cover the `/tags` page).

## 6. TagPicker.vue Implementation Record

### 6.1 Deliverables

| Artifact                                                          | Description                                                                                                                                   |

| [app/types/records.ts](../app/types/records.ts) (one-line change) | `MAX_TAG_NAME` exported (was module-local) so the picker's input can reuse the schema bound as its `maxlength` attribute. No behavior change. |

### 6.2 Component contract

- **`v-model: string[]`** (`defineModel`) — selected **tag IDs**; defaults to `[]`. This is exactly the `tagIds` shape of `RecordInputSchema`, so 1.3's `RecordForm` binds it directly, and the 1.4 list filter can reuse the same toggle semantics (product-design §6.2: "tag row = currently active tags (tap to toggle)").
- **`disabled?: boolean`** — freezes chips and creation while a parent form is submitting.

### 6.3 Design decisions

- **Zero tag props — the shared state _is_ the API.** The picker consumes `useTags()` directly (`predefinedTags` name-ordered, then `customTags` newest-first) and calls `ensureLoaded()` on mount; skeleton chips show while the first load is in flight. Every consumer (forms, filters, future `/tags` page) therefore renders the same list and sees mutations instantly — no prop drilling, no per-consumer fetching.
- **Toggle chips** are `UButton` pills: `solid`/`primary` when selected vs `soft`/`neutral` when not, with `aria-pressed` for assistive tech. Tap targets stay compact (`size="sm"`) per the mobile-first preference.
- **Inline create flow**: the dashed `+ Add tag` chip swaps to a compact `UInput` (auto-focused via UInput's exposed `inputRef`, `maxlength = MAX_TAG_NAME`, Enter submits / Esc cancels). Success closes and toasts; **failure keeps the input open** so the name can be corrected without retyping — matching the immediate-feedback UX preference.
- **Duplicate handling is two-layered.** A case-insensitive pre-check against the current state turns "create an existing name" into _select that tag_ (+ info toast), saving a round trip; the DB's unique violation (mapped to a friendly message by `createTag`, §3.3) remains the backstop for races. In both cases the resulting tag ends up selected.
- **Toasts** go through `useToast()` and render via the `UApp` Toaster wired into the shell in 1.1 — no extra provider.

| [app/components/TagPicker.vue](../app/components/TagPicker.vue) (refactor)  | Slimmed to chips + selection only; delegates creation to `TagCreateInline` and selects the emitted tag. Behavior unchanged (re-verified by SFC compile smoke).       |

### 7.2 Design decisions

- **The page holds no data logic.** It consumes `useTags()` directly (`predefinedTags`, `customTags`, `deleteTag`), calls `ensureLoaded()` on mount, and renders skeleton sections while the first load is in flight — same shared state as the picker, so a delete here is instantly reflected in any open record form.
- **Mock fidelity, scoped to the plan.** The mock's per-row `◻` checkbox ("use in filter") is the 1.4 list-filter concept and is intentionally absent here; this page implements list + delete (+ create, per the mock's `+`).
- **Predefined tags are read-only** — rows render the name with no affordance; RLS would reject any mutation anyway (§3.4).
- **Delete skips a confirm dialog** and toasts success ("records using it were untagged"). Rationale: a tag is recreatable in seconds and its loss is recoverable, the mock draws the delete as an inline `[x]`, and a modal-per-tap fights the compact mobile UX. Per-row pending state (`deletingId`) drives the button's loading spinner and prevents double deletes.
- **Creation reuses `TagCreateInline`** (the extraction above) instead of duplicating ~30 lines of dup-check/toast logic; its `created`/`existing` events need no handling here because the shared state updates globally.
- **Back link targets `/`** (records home, built in 1.4) — consistent with the bottom nav's Records tab; until 1.4 it 404s, same as every other nav target noted in the 1.1 doc.
- Zero-custom-tags empty state points users to the inline create and the record form.
