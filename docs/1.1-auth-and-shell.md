# Step 1.1: Authentication & Shell — Implementation Record

This document records the implementation process and verification results for the deliverables of **Task 1.1 (Authentication & Shell)** as defined in [development-plan.md](./development-plan.md) and [tech-design.md](./tech-design.md):

1. The **global auth guard** (§1–5 below).
2. The **auth pages** — `login`, `register`, `verify-email`, `reset-password` (§6 below).
3. The **main app shell** — toast provider, layout container, mobile bottom nav (§7 below).

Task 1.1 is therefore complete.

---

## 1. Overview & Objectives

Task 1.1 kicks off Phase 1 (MVP). Its first unit of work is the **global route guard**: every page in the app must be reachable only with an active Supabase session, except the four auth entry points that must stay public:

- `/login`
- `/register`
- `/reset-password`
- `/verify-email`

Because the guard runs before any auth page exists yet, this task is purely middleware-side; it produces no UI.

### Why a custom middleware is required

`nuxt.config.ts` sets `supabase: { redirect: false }`, deliberately opting out of `@nuxtjs/supabase`'s built-in auth redirect so that we control the flow. Inspecting the module (`node_modules/@nuxtjs/supabase/dist/module.mjs`) confirms the consequence:

```ts
if (mergedOptions.redirect) {
  addPlugin(resolve(runtimeDir, 'plugins', 'auth-redirect'))
}
```

With `redirect: false` the module's `auth-redirect` plugin is **not** registered — no login-page redirect happens at all. Our own `auth.global.ts` middleware fills that gap (and, being the only global auth middleware, never conflicts or double-redirects).

## 3. Design Decisions

### 3.1 Public-path whitelist as a `Set`

```ts
const PUBLIC_PATHS = new Set(['/login', '/register', '/reset-password', '/verify-email'])
```

- The check is `PUBLIC_PATHS.has(to.path)` — **not** `to.fullPath`. Supabase auth callbacks append query params (`?token_hash=...&type=email`) or hash fragments (`#access_token=...`) to the whitelisted pages; comparing `to.path` keeps those callback URLs public while matching every other route exactly.
- The whitelist is exactly the four routes from the development plan. No route pattern matching (prefix/glob) is needed at this stage.

### 3.2 Session check via `useSupabaseUser()`

```ts
const user = useSupabaseUser()
if (!user.value) {
  return navigateTo('/login')
}
```

- `useSupabaseUser()` is backed by `useState('supabase_user')`, populated by the module's `supabase.server` plugin (enforced `pre`, i.e. before route middleware on SSR) from the HttpOnly session cookie, and kept in sync client-side by the `supabase.client` plugin. The middleware therefore sees a settled value on both server and client — no loading-state waiting is required.
- Checking the **user** (rather than the session) matches the plan/tech-design wording ("checks `useSupabaseUser()`") and rejects nothing extra: an expired-but-present cookie decodes to `null` on the server and redirects correctly.
- The redirect target is a plain `/login` per the plan. No `redirect` query param / cookie is persisted yet — when the login page is built (next 1.1 task) we can decide whether to restore the originally requested route.

### 3.3 Global by naming convention

The file is named `auth.global.ts`, so Nuxt registers it as a **global** middleware (runs for every route) without any registration code. No `definePageMeta` overrides exist on pages yet; per-route exceptions will not be needed because the whitelist already covers all public routes.

### 6.3 Design decisions

#### 6.3.1 Email-verification callback — handled on the whitelisted page, no `/confirm` route

`@supabase/auth-js@2.112.4` defaults are `flowType: 'implicit'` and `detectSessionInUrl: true`. Two link formats must therefore be supported, and both arrive on the page whose path we already whitelist:

- **Implicit-flow links** append the session to the URL hash (`#access_token=…`); the Supabase client auto-detects it. `verify-email.vue`/`reset-password.vue` confirm with `getSession()` — no manual work.
- **PKCE-style links** carry `?token_hash=…&type=email|recovery`; the client does not auto-handle these, so the pages call `verifyOtp({ type, token_hash })` explicitly.

Both pages run this logic in `onMounted` (client-only — hash fragments are never visible to SSR). No extra `/confirm` route is added; the module's `ssr:false` callback rule only applies when `redirect: true`, which we deliberately keep off.

#### 6.3.2 Password reset as a two-step view on one page

`reset-password.vue` covers both halves of the flow the plan lists ("password recovery request **&** token-based password update form"):

- No session & no token → **request** form; `resetPasswordForEmail(email, { redirectTo: <origin>/reset-password })`; success shows a generic "sent" state that does not reveal whether the account exists.
- Session (implicit hash) or a verified `token_hash` (recovery) → **set** form; `updateUser({ password })`, then `signOut()` and `navigateTo('/login?reset=1')` so the user re-authenticates with the new password (the login page surfaces a confirmation alert).

#### 6.3.3 Shared schemas (`app/types/auth.ts`)

- Email: trimmed, required, ≤ 254 chars, pragmatic regex.
- Password: ≥ 8 chars + at least one digit (product rule). Passwords are **not** trimmed (a password of spaces should fail length, not be silently changed).
- Confirm-password checks live in the schema (`refine` on `['confirmPassword']`) so mismatch errors show under the right field.
- Register deliberately omits the `name` field from the product mock: the plan lists email/password only, and the current data model has no profile table (can be added as `user_metadata` later if wanted).

#### 6.3.4 `emailRedirectTo` must be an absolute URL

Supabase requires redirect targets in the project's allow-list. `register.vue`/`reset-password.vue` therefore build the URL from `window.location.origin` at submit time. When a live project is configured, `/verify-email` and `/reset-password` must be added to the dashboard's redirect allow-list.

### 7.3 Design decisions

- **`UApp` as the toast provider.** Nuxt UI v4 ships `UApp` precisely for this role (props: `toaster`, `tooltip`, `locale`, `portal`). Wrapping once in `app.vue` gives every future feature (e.g., "Record saved" toasts in 1.3) `useToast()` with zero extra wiring.
- **Conditional shell instead of a layout system.** The auth pages (§6) each render their own full-screen centering; a global container would double-frame them. `app.vue` therefore branches on `PUBLIC_AUTH_PATHS.has(route.path)`: bare `NuxtPage` for auth routes, container + nav for everything else. No `layouts/` directory was introduced — the plan doesn't call for one, and the branch is explicit and readable. Crossing the auth/app boundary remounts the page (different `NuxtPage` branch), which is the desired behavior anyway.
- **Shared `PUBLIC_AUTH_PATHS` constant.** The guard whitelist and the shell's nav-visibility check must stay in sync forever (add a public page → update both, or the shell breaks). One constant in `app/utils/` (auto-imported everywhere) removes the drift risk; the guard file was updated to consume it.
- **Active-tab matching.** Records uses an exact match — a prefix rule would light it up on _every_ route (`/`…). The other tabs use prefix matching so nested pages stay highlighted (e.g., `/records/new` keeps Add active; a future `/records/[id]` detail page will also fall under Add — acceptable for now).
- **`md:hidden` + safe area.** The plan scopes the bottom nav to mobile; desktop navigation arrives with the later list/settings work. The safe-area padding keeps the bar above the iOS home indicator.
- **Links precede pages.** All five nav targets belong to later tasks (1.3–1.5, 2.2–2.3) and 404 until those land — expected given the plan builds the shell before the pages. The smoke test therefore verifies visibility logic, not navigation.
