## 3. Design Decisions

- **Card = one link.** The entire card is the tap target (`NuxtLink` → `/records/[id]`), matching the mock's "tap a card → detail" and giving a full-width mobile hit area; no inner buttons exist yet (quick delete is a later per §6.2 notes).
- **Layout follows the mock's three lines**, not a corner badge: quoted content (bold), `type · meaning` (muted, type capitalized via CSS `capitalize`), and a footer row with tag chips + `ml-auto` time. Tag-less records keep the time row (right-aligned) so card rhythm stays consistent.
- **Plain-span badges, not `UBadge`.** A list renders N cards; skipping the component runtime keeps the DOM light. The pill styling (`rounded-full bg-accented`) mirrors the detail page's chips.
- **Explicit imports over Nuxt auto-imports.** `formatRelativeTime` is imported explicitly (`~/utils/datetime`), and the SFC uses no Nuxt-only APIs, so the bare-vitest environment (which lacks Nuxt auto-import processing; [vitest.config.ts](../vitest.config.ts) provides only the `~` alias + vue plugin + happy-dom) compiles the component unchanged in tests.
- **`formatRelativeTime` is pure with injectable `now`.** Ladder: `< 1m → "just now"`, then `m/h/d/w` buckets (floor), `≥ 30d → "Sep 12, 2026"` absolute; negative diffs (clock skew) clamp to `just now`. `now` defaults lazily per call.
- **Hydration note:** relative time differs between server render and client by seconds — but the list page will fetch client-side (same `onMounted` pattern as [1.2 doc](./1.2-tag-management.md)), so cards render client-only and there is no SSR hydration surface.

## 6. Index Page Implementation Record

### 6.1 Deliverable

[index.vue](../app/pages/index.vue) implements the mock in [product-design.md §6.2](./product-design.md): `My Records [ + ]` header, search box, type chip row, `[Tag ▾] / [Newest ▾]` controls, active-tag chip row, card list, and both empty states. Data comes entirely from `useRecords().fetchRecords` (§1.3) and the shared `useTags` state (§1.2) — no new server surface (architecture rule 1).

### 6.2 Design decisions

- **Dropdowns for tag/sort controls** (compact-control preference), per the mock's `[Tag ▾]` / `[Newest ▾]` line: `USelectMenu` (multiple, `value-key="value"` — unlike `USelect`, its `valueKey` does **not** default to `'value'`, so objects would otherwise model the whole item) over all predefined+custom tags, and a `USelect` for the three sort orders.
- **Active-filter chip row below the controls** mirrors the mock: one removable chip per active tag (tap `×`), plus a `+` linking to `/tags` (mock: "'+' for tag manager") — creation/management stays in the tags page, filtering stays here.
- **Debounced search (300 ms):** the input ref and the query ref are separate; only the debounced ref feeds `fetchRecords`, so typing is instant and the network sees one request per pause. Trim + the composable's `,()` sanitization (§3.4) are the full input path.
- **Infinite scroll via `IntersectionObserver`** on a sentinel rendered right below the last card with `rootMargin: 400px` — the next page pre-fetches before the user hits the bottom. `loadMore()` is a no-op while the first load or another `loadMore` is in flight (`loading`/`loadingMore`/`hasMore` guards).
- **Stale-response guard:** a `fetchGen` counter increments on every `loadFirst`/`loadMore`; late responses from a superseded filter state are discarded instead of mutating the newer list (filters can change faster than PostgREST answers).
- **Empty states distinguish the two plan cases:** no records at all → "No records yet" + _Add record_ CTA; filters active → "No matches" + _Clear filters_ button (resets search/type/tags/sort in one tick; Vue batches the watcher into a single refetch).
- **Client-side fetching only** (same `onMounted` pattern as `tags.vue`): keeps the auth session/token out of SSR, avoids hydration drift from relative times (§3), and Nuxt's default remount-on-navigate means returning from create/edit/delete refetches fresh data for free.
- Page count display: end-of-list caption shows `N records` after the final page; the "infinite" affordance is the spinner row while appending.
