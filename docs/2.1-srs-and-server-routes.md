## 2. Grade Transition Semantics

| Grade    | Interval                                   | consecutive\_pass     | Status                 |
| -------- | ------------------------------------------ | --------------------- | ---------------------- |
| `forgot` | resets to **1**                            | **0** (streak broken) | `learning`             |
| `hazy`   | `max(1, round(current / 2))`               | **0** (not a pass)    | `learning`             |
| `know`   | next rung of ladder `[0, 1, 3, 7, 14, 30]` | `+1`                  | `mastered` on 3rd pass |
| `easy`   | `min(30, max(1, round(current × 3)))`      | `+1`                  | `mastered` on 3rd pass |

Design decisions worth noting (deviations / clarifications vs. the raw spec snippets):

- **`know`** **handles off-ladder intervals correctly.** The tech-design sketch used `INTERVALS.indexOf(current) + 1`, which silently returns ladder index 0 (interval 0!) for any off-ladder value — e.g. an interval of 2 left by a previous `easy`, or 15 left by `hazy`. The implementation instead picks the **smallest ladder value strictly greater than the current interval** (2 → 3, 9 → 14, 29 → 30, 30 → 30).
- **`easy`** **is clamped to ≥ 1 day.** The literal `min(30, round(current × 3))` yields **0** for a fresh record (interval 0), which would leave the card instantly due again. Clamping only affects that one case (all other intervals map to ≥ 3); a new card graded `easy` now schedules +1 day.
- **`hazy`** **breaks the pass streak.** "3 _consecutive_ `know`/`easy` passes" means a `hazy` is not a pass, so `consecutive_pass` resets to 0 (same as `forgot`).
- **Mastery caps the interval at 30** and `forgot` pulls a mastered record back into `learning` with a 1-day interval (re-enters the queue — the natural forgetting path).
- **`nextReviewAt`** **uses calendar-day arithmetic** (`setDate`), so "1 day" means the same wall-clock time tomorrow; the input `Date` is never mutated.

## 3. Route Design Decisions

- **Session reads use the caller's JWT** (`serverSupabaseClient` from the module's `#supabase/server` alias), so RLS scopes `review_states` and `records` to the owner — no service key involved for reads (architecture rule 2). The route fetches the `limit` most-overdue states, then a second query fetches the records with their tags embed (`record_tags(tags(*))`, same shape as the client's `useRecords` mapper), merges and **shuffles (Fisher–Yates)** to remove next-review-order bias. `totalDue` (exact count, `head: true`) is returned alongside so the 2.2 review-index page can render "N items due today" without a second endpoint.
- **Grade mutations use the service-role client** (tech-design §7) but never trust the body: identity comes from the cookie session (`requireUserId` → JWT claims `sub`), and ownership is re-checked explicitly with `.eq('user_id', userId)` before any write, because RLS does not bind the service client (architecture rules 3 & 4).
- **"Transaction" caveat:** PostgREST has no multi-statement transaction, so the route performs the `review_states` upsert first and the `review_events` append second. If the append fails, the schedule has already moved (stats lose a single event); the client can retry, which re-grades from the fresh state. A future Postgres RPC could make this atomic if stats precision ever demands it.
- **Missing** **`review_states`** **rows grade from defaults** (interval 0, streak 0) and are created via upsert — records created before this feature or with a failed init are recoverable instead of 404-ing forever.
- **Auth is checked before body validation**, so anonymous callers get a clean `401 Not authenticated` rather than a schema error; invalid bodies get `400` with the Zod issues attached as error `data`.
- **Service client resolution** covers both key mappings — the `@nuxtjs/supabase` module's (`SUPABASE_SERVICE_ROLE_KEY` → `supabase.secretKey`) and nuxt.config's own `supabaseServiceRoleKey` — and is cached per-request on `event.context`. When the key is absent the routes fail with an explicit 500 ("Service-role Supabase client is not configured") instead of an opaque Supabase error.
- **New dependency:** `@supabase/supabase-js` was promoted to a direct dependency (`^2.112.4`, previously only transitive via `@nuxtjs/supabase`) because server code imports `createClient` directly.
