## 2. Design Decisions

- **Counts aggregate over `review_states`, not `records.learning_status`.** The grading route (`grade.post.ts`) updates `review_states.status` but never syncs `records.learning_status`, so a records-based count would read stale zeros forever. This follows [tech-design.md §7](./tech-design.md) ("Total / learning / mastered counts (aggregate over `review_states`)").
- **`learning` = `new` + `learning` (not yet mastered).** A `review_states` row starts as `new` and is due immediately (`next_review_at` defaults to `now()`), so never-reviewed records are already in the active loop. With this definition the three KPI cards reconcile (`Total ≈ Learning + Mastered`) instead of leaving the `new` bucket invisible.
- **`dueToday` rides along in the response**, using the exact same predicate as `GET /api/review/session` (`next_review_at <= now`, status not mastered). The stats page needs it for its "due today" callout; computing it here mirrors the session route's `totalDue` precedent and saves a second request.
- **Timezone is a query parameter:** `?tz=` takes an IANA name (the future page will pass `Intl.DateTimeFormat().resolvedOptions().timeZone`), validated with a `Intl.DateTimeFormat` construction — invalid names get a clean `400`, missing falls back to `UTC`. Day keys are produced via `formatToParts` (immune to runtime locale format quirks) and the previous-day walk uses UTC-anchored arithmetic, so month, leap-year, and DST boundaries stay correct.
- **Streak semantics:** the run ends at today or yesterday — "not reviewed _yet_ today" does not break the streak, but the first missing day before that does. Zero activity → 0.
- **Reads use the caller's JWT** (`serverSupabaseClient`), so RLS scopes all three tables to the owner — no service key on this route (architecture rule 2). The five queries (4 head-counts + event timestamps) run in `Promise.all`.
- **Event aggregation happens in JS** on a single fetched `reviewed_at` column: PostgREST has no `date_trunc` grouping, and personal-scale volumes (tens of events/day) make a full column scan acceptable. If volume ever matters, a Postgres RPC (`date(reviewed_at) at time zone …` group-by) is the upgrade path.
- **Pure math lives in `server/utils/stats.ts`** with the route as thin glue — same testability split as `srs.ts`.
- **Known build warning (pre-existing, not introduced here):** Rollup warns about the `#supabase/server` barrel re-export of `serverSupabaseClient`; the identical warning already fired for `session.get.ts` before this task. The build succeeds; deep-importing the module file is the fix if it ever matters.
